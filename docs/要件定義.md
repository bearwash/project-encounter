# 📱 Project Encounter (仮) 要件定義書

## 1. プロダクト概要

- **コンセプト**: 「歩く日常が少し楽しくなる。あの頃の『すれ違うワクワク』を現代のスマホで再現するアバターアプリ」
- **コアバリュー**: 位置情報に依存しない、純粋な「物理的近接」による偶発的なコミュニケーション体験の創出。
- **ターゲット**:
  - **プライマリ**: 過去の携帯ゲーム機での「すれ違い体験」にノスタルジーを感じる若年層・学生（特にキャンパスなど人が密集する環境）。
  - **セカンダリ**: 日常の移動に「受動的でゆるい繋がり」を求めている層。

## 2. システム構成・技術スタック

- **アーキテクチャ**: Tauri v2 (iOS / Android クロスプラットフォーム)
- **フロントエンド (UI)**: Next.js (React), Tailwind CSS, @tanstack/react-query
  - ※ Vibe Coding（AI生成）を前提としたモダンフロントエンド構成。
- **バックエンド (コアロジック)**: Rust
  - Tauri Plugin または FFI 経由で OS ネイティブの BLE API（CoreBluetooth / Android Bluetooth API）を制御。
- **データベース**: SQLite (Tauri Plugin SQL 経由でローカル保存)

## 3. 体験設計（UX）と画面構成

### 3.1 コア UX フロー（開けた時のサプライズ）

1. **潜伏**: ユーザーはアプリを裏側に回し（またはウォークモードで）スマホをポケットに入れて移動。
2. **すれ違い（サイレント）**: バックグラウンドで BLE 通信が成立。相手のデータをローカル DB に保存するが、OS のプッシュ通知は一切出さない。
3. **エンカウント**: ユーザーがアプリを立ち上げた際、未読のすれ違いデータがあれば、専用のポップアップ演出へ遷移する。

### 3.2 主要画面（UI）

#### A. 新規エンカウント・ポップアップ画面 (Sequential Popup)

- アプリ起動時に未読データがある場合に表示される全画面オーバーレイ。
- 「ENCOUNTER!」のネオン UI と共に、相手のアバターと一言メッセージが表示される。
- ★**連続表示仕様**: 未読が複数人いる場合、「次へ」を押すと現在のアバターが消え、次のアバターが順番に入場してくる（3DS の広場入場リスペクト）。

#### B. ホーム画面（すれ違い履歴リスト / EncounterList）

- 既読のすれ違いユーザーがリスト状に並ぶメイン画面。
- 表示項目: アバターアイコン、名前、最終すれ違い日時、累計すれ違い回数。

#### C. プロフィール設定画面

- 自分の名前、一言メッセージ（例: 30 文字以内）、アバターの見た目（パーツコード）を設定。

#### D. ウォークモード画面（iOS 用 省電力待機画面）

- 確実なすれ違いを実現するため、画面を暗くしてアプリをフォアグラウンドで立ち上げっぱなしにする専用モード。誤作動防止のロック機能付き。

### 3.3 ビジュアルトーン・インスピレーション

#### 挙動のインスピレーション源（体験のコア）

- 任天堂機（**DS / 3DS**）における **「アプリを開いた瞬間に、新しい出会いが待っている」体験** を現代のスマホに再構築する。
- 特に **3DS の『すれちがい Mii 広場』の入場シーン** を強く意識し、「**開けた時のサプライズ**」を UX の中心に据える。
- **連続ポップアップ方式**: 未読のすれ違いデータが複数ある場合、1 度に全員を表示するのではなく、**1 人ずつ「挨拶（一言メッセージ）」をしては次の人に交代する** 流れを作る。
- **賑わいの可視化**: 単なる履歴のテキストリストではなく、これまですれ違ったアバターたちが画面内に集まり、思い思いに過ごしている **「広場」のような空間表現** を目指す。

#### アバターの動的挙動（必須要件）

- アバターは **静止画ではなく、常に何らかの愛嬌ある動き** を持つ。
  - **入場**: 「次へ」を押した際、画面外から **トコトコと歩いて入ってくる**、または **ヒョコッと飛び出してくる**。
  - **待機**: メッセージを表示している間も、小さく呼吸する、足踏みする、きょろきょろするなど、生きているような **アイドリング動作** を入れる。
  - **退場**: フェードアウトではなく、軽くお辞儀をする、手を振って横にハケるなどの挙動を含める。
- スマホのバッテリーや描画負荷を考慮し、**Web 技術（CSS アニメーションや Framer Motion）で軽く動かせるシンプルなパーツ構成（スプライト切替など）** で実装する。

#### 目指すビジュアルと世界観（トーン＆マナー）

- **ノスタルジック・ポップ**: サイバーやダークな世界観ではなく、**明るく、親しみやすく、日常の延長にあるような** クリーンでポップな UI デザイン。
- **キャラクターデザイン**: 3DS の雰囲気を踏襲しつつも独自性を持たせるため、**ボクセルアート（3D ドット）** や、**レトロ可愛いピクセルアート** を採用する。無機質なデータ通信でありながら、どこか **おもちゃのような温かみと愛嬌** を感じさせるデザイン。
- **UI の質感**: ボタンを押したときの「ポンッ」という **心地よいバウンスアニメーション** や、**角の丸いウィンドウ** など、触っていて楽しい **「おもちゃ箱」のような手触り** を重視する。

#### 明確に避けるもの（法的リスク・UX の観点）

- **任天堂 IP の直接的な模倣**: Mii の頭身比・顔パーツの構成・デフォルトの配色の完全コピー。
- **商標・固有名詞**: 「すれ違い通信」「StreetPass」「広場」といった任天堂の登録商標・固有名詞のアプリ内テキストでの使用。
- **過剰なエフェクト**: 派手な発光やネオン、重厚すぎる 3D エフェクトなど、バッテリーを消耗させ「日常的に裏で動かす」というコンセプトを阻害する描画。

## 4. 機能要件と通信ルール

### 4.1 すれ違い通信の仕様（BLE）

- **通信方式**: Bluetooth Low Energy (BLE) の P2P アドレス交換。
- **ハイブリッド待機**:
  - **通常時**: アプリ専用の Service UUID を指定したバックグラウンドスキャン＆アドバタイズ。
  - **ウォークモード時**: フォアグラウンドでの高頻度スキャン＆アドバタイズ。
- **クールダウン設定**: 「8 時間」
  - 同じユーザー ID の相手とは、前回すれ違った時刻から 8 時間経過するまで再度のすれ違いログを記録しない（テストプレイ時は 1 分等に短縮可能にする）。

### 4.2 BLE ペイロード（交換データ）

通信の失敗を防ぐため、1 回のハンドシェイクで交換するデータは最小限の文字列（JSON 等）とする。

```json
{
  "id": "A1B2C3D4",
  "name": "Neko-9",
  "avatar": "base01_top03_bot02",
  "msg": "最近はRust勉強中！"
}
```

## 5. データ設計（ローカル SQLite スキーマ）

サーバーは介在せず、すべてのデータは端末内に閉じて保存される。

### `my_profile` テーブル (自己データ)

| カラム | 型 |
| --- | --- |
| `user_id` | UUID |
| `display_name` | String |
| `avatar_code` | String |
| `message` | String |

### `encounter_logs` テーブル (トランザクション履歴)

| カラム | 型 |

| `encountered_at` | Timestamp |

### `users_cache` テーブル (すれ違った相手のプロフィール)

| カラム | 型 |
| --- | --- |

| `display_name` | String |
| `avatar_code` | String |
| `message` | String |

## 6. 法的・セキュリティ要件

- **位置情報の非取得**: GPS や CoreLocation などの座標データは一切取得・保存・送信しない。物理的な電波の到達のみを「すれ違い」の証明とする。
- **知的財産権の回避**:
  - 「すれ違い通信」「StreetPass」等の商標は使用しない。
  - Mii のような著作権侵害リスクのあるデザインは避け、ピクセルアートやボクセル・ローポリゴンなど、抽象化された「データオブジェクト」としての独自のキャラクターデザインを採用する。
- **プライバシー**: 通信内容はローカル DB にのみ保存し、中央サーバーへ履歴をアップロードしない。

## 7. 開発フェーズ（マイルストーン）

### Phase 1: MVP（最小限の価値検証） 👈 現在ここ

- Next.js + Tailwind による UI モックアップ（Vibe Coding）。
- Tauri/Rust での BLE 通信プロトタイプ（ハンドシェイク検証）。
- 固定テキストの交換と、連続ポップアップ UI の結合。キャンパス内での実地テスト。

### Phase 2: アバターの拡張と動的生成

- LLM（ローカルまたは軽量 API）を活用した、タグ情報に基づく動的な会話生成。
- アバター表現のブラッシュアップ（WebGL/Three.js 等の導入検討）。

### Phase 3: AVATAVI STORE プラットフォーム化

- Go 言語等のバックエンドサーバー構築（アイテム購入・管理機能）。
- 着せ替えパーツ（服・帽子等）の仮想通貨/ポイントによる販売システムの導入。

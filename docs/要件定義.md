# 📱 Project Encounter (仮) 要件定義書

## 1. プロダクト概要

- **コンセプト**: 「歩く日常が少し楽しくなる。あの頃の『すれ違うワクワク』を現代のスマホで再現するアバターアプリ」
- **コアバリュー**: 位置情報に依存しない、純粋な「物理的近接」による偶発的なコミュニケーション体験の創出。
- **ターゲット**:
  - **プライマリ**: 過去の携帯ゲーム機での「すれ違い体験」にノスタルジーを感じる若年層・学生（特にキャンパスなど人が密集する環境）。
  - **セカンダリ**: 日常の移動に「受動的でゆるい繋がり」を求めている層。

## 2. システム構成・技術スタック

- **アーキテクチャ**: Tauri v2 (iOS / Android クロスプラットフォーム)
- **フロントエンド (UI)**: Next.js (React), Tailwind CSS, @tanstack/react-query
  - ※ Vibe Coding（AI生成）を前提としたモダンフロントエンド構成。
- **バックエンド (コアロジック)**: Rust
  - Tauri Plugin または FFI 経由で OS ネイティブの BLE API（CoreBluetooth / Android Bluetooth API）を制御。
- **ローカルデータベース**: SQLite (Tauri Plugin SQL 経由)
  - すれ違い履歴（誰といつ会ったか）、アプリ設定、自プロフィールを保持する。
- **クラウドバックエンド (BaaS)**: **Supabase** (Postgres + REST + Auth)
  - 役割は **「user_id ↔ 公開プロフィール (display_name / avatar_code / message) の名簿」のみ**。
  - すれ違い履歴は一切アップロードしない（履歴は端末ローカルに閉じる）。
  - Phase 3 で自前 Go バックエンドへの置換を予定。Supabase は Phase 1〜2 のスキャフォールド。

## 3. 体験設計（UX）と画面構成

### 3.1 コア UX フロー（開けた時のサプライズ）

1. **潜伏**: ユーザーはアプリを裏側に回し（またはウォークモードで）スマホをポケットに入れて移動。
2. **すれ違い（サイレント）**: バックグラウンドで BLE 通信が成立。相手のデータをローカル DB に保存するが、OS のプッシュ通知は一切出さない。
3. **エンカウント**: ユーザーがアプリを立ち上げた際、未読のすれ違いデータがあれば、**「公園の入口」シーン** が起動する。
   - 上部のストリップ UI に「今日のすれ違い：N 人」
   - すれ違った相手たちが隊列で並んで歩いてきて、1 人ずつユーザー自身のアバターと対面
   - 2 回目以降の相手とは **ハイタッチ + 「TAP!」エフェクト**、初回は **会釈**
   - 吹き出しで「やっと N 回目！」のシステムプレフィックス + 本人の一言メッセージ
4. **広場へ**: 全員と挨拶し終わると、カメラがゲートに向かってパンし、ユーザーと挨拶した全員でゲートをくぐって広場ビューに到着する。

### 3.2 主要画面（UI）

#### A. 新規エンカウント・対面挨拶シーン（Encounter Greeting）

- アプリ起動時に未読データがある場合に表示される **全画面の "公園の入口" シーン**。
- 舞台は公園のゲート前。ユーザー自身のアバター（左）と相手のアバター（右）が **斜め内向き 2 ショット構図** で対面する。
- 上部のストリップ UI に「今日のすれ違い：N 人」「i / N」のインジケータを常時表示。
- ★**連続挨拶仕様**: 相手たちは画面奥の隊列に並んで待機し、1 人ずつ前に出てくる。タップで挨拶を進める。
  - **2 回目以降**の相手とはハイタッチ動作 + 「TAP!」エフェクト
  - **初回**の相手は会釈で挨拶
  - 吹き出しに **システムプレフィックス（「やっと 3 回目！」等）+ 本人メッセージ** を表示
- 全員終了後はカメラパン + ゲート通過で広場ビュー（B）へ遷移。

#### B. ホーム画面（広場ビュー / EncounterPlaza）

- 既読のすれ違いユーザーが、**横スクロールの「夕方の公園」**を歩き回る広場画面。
- 舞台は **薄明るい夕方の公園**（マジックアワー固定）。街灯・ベンチ・桜の木が配置された 3 層パララックス背景。
- カメラは横視点（2D 横スクロール）。アバターは画面の左右にトコトコ歩いたり、立ち止まって周りを見たりする。
- 同時表示は **最大 30 人**。それ以上は「スクロールで裏にもっといる」表現（左右にスクロール）で全員アクセス可能にする。
- アバタータップで個人詳細（最終すれ違い日時、累計回数、メッセージ）を表示。
- **住人の卒業・間引きは行わない**。すれ違った住人は何ヶ月経っても広場に残り続ける（コレクション体験を最優先）。
- 空状態（すれ違い 0 件）では誘導テキストとウォークモードへの導線を表示。
- 設計の思想は **Wii の Mii パレード／チャンネル系の "賑わい"**。リスト的な情報密度より、**「いつ開いても、知らない誰かたちが今日も広場にいる」生活感**を優先する。

#### C. プロフィール設定画面

- 自分の名前、一言メッセージ（例: 30 文字以内）、アバターの見た目（パーツコード）を設定。

#### D. ウォークモード画面（iOS 用 省電力待機画面）

- 確実なすれ違いを実現するため、画面を暗くしてアプリをフォアグラウンドで立ち上げっぱなしにする専用モード。誤作動防止のロック機能付き。

### 3.3 ビジュアルトーン・インスピレーション

#### 挙動のインスピレーション源（体験のコア）

- 任天堂機（**Wii / DS / 3DS**）における **「アプリを開いた瞬間に、新しい出会いが待っている」体験** を現代のスマホに再構築する。
- 特に **Wii の Mii パレード／Mii チャンネルの "賑わい"** と、**3DS『すれちがい Mii 広場』の入場サプライズ** を組み合わせ、「**開けた時のサプライズ**」と「**いつ開いても誰かが広場で生活している**」の両方を体験の核に据える。
- **連続ポップアップ方式**: 未読のすれ違いデータが複数ある場合、1 度に全員を表示するのではなく、**1 人ずつ「挨拶（一言メッセージ）」をしては次の人に交代する** 流れを作る。
- **広場への定住**: ポップアップを終えたアバターは消えずに、**そのまま「広場」に合流して住人になる**。再起動しても住人は広場に居続け、新しい住人がワラワラ追加されていく。

#### アバターの動的挙動（必須要件）

- アバターは **静止画ではなく、常に何らかの愛嬌ある動き** を持つ。
  - **入場**: 「次へ」を押した際、画面外から **トコトコと歩いて入ってくる**。
  - **待機（ポップアップ中）**: メッセージを表示している間も、小さく呼吸する、足踏みする、きょろきょろするなど、生きているような **アイドリング動作** を入れる。
  - **広場での生活**: ポップアップ終了後は広場に合流。**ランダムに左右に歩く / 立ち止まる / 周りを見渡す** のループで「住人感」を出す。
- 描画は **SVG パーツの重ね合わせ + CSS アニメーション** で実装する（[specs/avatar.md](./specs/avatar.md) 参照）。Framer Motion 等の重いランタイムは使わず、`@keyframes` で軽量に動かせる構成を維持する。

#### 目指すビジュアルと世界観（トーン＆マナー）

- **ノスタルジック・ポップ**: サイバーやダークな世界観ではなく、**明るく、親しみやすく、日常の延長にあるような** クリーンでポップな UI デザイン。
- **キャラクターデザイン**: **2.5D ベクターキャラクター**を採用する。Mii / Memoji / Apple Mimoji / Telegram スタンプの中間ゾーンを狙う、**人型の可愛いデフォルメ**。MVP は SVG パーツ + グラデ/シャドウ/ハイライトで「**フラットだけど少し立体感のある**」表現。完全な 3D は Phase 2 で R3F + glTF に進化予定（§7）。ピクセルアートやボクセル（旧方針）は採用しない。
- **UI の質感**: ボタンを押したときの「ポンッ」という **心地よいバウンスアニメーション** や、**角の丸いウィンドウ** など、触っていて楽しい **「おもちゃ箱」のような手触り** を重視する。

#### 明確に避けるもの（法的リスク・UX の観点）

- **任天堂 IP の直接的な模倣**: Mii の頭身比・顔パーツの構成・デフォルトの配色の完全コピー。Mii と「人型デフォルメ」というジャンルは共有しつつ、頭身・顔の構造・配色設計で明確な差別化を行う。
- **商標・固有名詞**: 「すれ違い通信」「StreetPass」「Mii パレード」など、任天堂の登録商標・固有名詞のアプリ内テキストでの使用。
- **過剰なエフェクト**: 派手な発光やネオン、重厚すぎる 3D エフェクトなど、バッテリーを消耗させ「日常的に裏で動かす」というコンセプトを阻害する描画。

## 4. 機能要件と通信ルール

### 4.1 すれ違い通信の仕様（BLE: ID-only ハイブリッド方式）

- **通信方式**: BLE の **Advertise / Scan を主経路** とする。
  - 自端末は **Supabase Auth の UUID（16 byte バイナリ）の `user_id` のみ** を Advertise し続ける。
  - Scan 側は、アプリ専用の Service UUID をフィルタ条件にして、相手の `user_id` を抽出してローカル DB に「ID + 受信時刻」だけ保存する。
  - mobile では Service UUID advertise + GATT read を主経路にする。128-bit Service UUID に 16 byte `user_id` を Service Data として同梱すると BLE Legacy Advertise のサイズ上限を超えるため、Android でも GATT read を標準経路にする。desktop は Service Data を受信できる場合のみ即時処理する。
  - Service Data 経路では通信時間は数百ミリ秒以下。GATT fallback は `user_id` 取得のみに限定し、プロフィール本体は交換しない。
- **プロフィールはクラウドから取得**:
  - 受信時点では相手の名前・アバター・メッセージは未取得。アプリがフォアグラウンドになったタイミングで、未取得の `user_id` 一覧を Supabase に問い合わせて一括ダウンロードし、`users_cache` に保存する（[specs/profile-sync.md](./specs/profile-sync.md)）。
- **ハイブリッド待機**:
  - **通常時**: アプリ専用の Service UUID を指定したバックグラウンド Scan & Advertise。
    - iOS は CoreBluetooth の State Preservation / Restoration を使い、一度プロフィール作成・同意・Bluetooth 権限付与まで済んだ後は、OS が許す範囲でバックグラウンド復元を試みる。ただし初回起動前、ユーザーがアプリを force quit した後、Bluetooth が無効な状態では復元されない。
    - Android は BLE 起動中に Foreground Service を立て、アプリ画面を閉じても OS による停止を受けにくい状態で Scan & Advertise を継続する。加えて `PendingIntent` scan を保険として登録し、プロセスが一度落ちても OS が scan result を配信できる場合は `BroadcastReceiver` で GATT read を試みる。通知権限が必要な端末では、Bluetooth 権限と合わせて通知権限も要求する。
  - **ウォークモード時**: フォアグラウンドでの高頻度 Scan & Advertise。**自動終了は一切行わず**、ユーザーが手動で停止するまで稼働する（バッテリー警告 UI で利用者に判断材料を提供）。
- **すれ違い通知**:
  - ロック中や画面外で native plugin が新規 `user_id` を検出した場合、OS の通知権限が許可されていれば「すれ違いました」通知を出す。
  - 通知本文にはプロフィール本体や位置情報を含めない。プロフィール名・アバター・メッセージはアプリ復帰後の profile fetch で表示する。
- **クールダウン設定**: 「8 時間」
  - 同じユーザー ID の相手とは、前回すれ違った時刻から 8 時間経過するまで再度のすれ違いログを記録しない（テストプレイ時は 1 分等に短縮可能にする）。

### 4.2 BLE Advertise ペイロード

BLE Advertise で流すのは **Supabase Auth の UUID（16 byte バイナリ）のみ**。
プロフィール本体（display_name / avatar_code / message）は Supabase 経由で取得する（[specs/profile-sync.md](./specs/profile-sync.md)）。

```
Service UUID: <アプリ固有の 128-bit UUID>   # 全経路共通 (advertise / scan filter)
# desktop (btleplug): Service Data: 16 byte = user_id (UUID binary form)
# mobile  (iOS/Android): Service Data には載せず、GATT read characteristic で 16 byte を返す
#   (128-bit Service UUID + 16 byte を Service Data に同梱すると Legacy Advertise 31 byte を超えるため)
```

`user_id` は **ユーザーが Apple / Google / メールで明示ログインした Supabase Auth アカウントの UUID をそのまま採用**（衝突確率実質ゼロ）。ゲスト起動中は UUID を自動発行せず、BLE advertise も開始しない。ローカル DB と Supabase の双方で同じ UUID を主キーとして扱う。mobile では同じ 16 byte 値を GATT read characteristic から読む（iOS / Android 共通）。バイト順はネットワークバイト順 (RFC 4122 / big-endian)。
詳細は [specs/ble-handshake.md](./specs/ble-handshake.md) と [contracts/ble-payload.schema.json](./contracts/ble-payload.schema.json) を参照。

### 4.3 クラウドプロフィール（Supabase スキーマ概要）

```sql
-- profiles : 公開プロフィール名簿（履歴は一切持たない）
CREATE TABLE profiles (
  id           UUID PRIMARY KEY REFERENCES auth.users(id),
  display_name TEXT NOT NULL,
  avatar_code  TEXT NOT NULL,             -- b{NN}_h{NN}_o{NN}_f{NN}
  message      TEXT,
  updated_at   TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;

-- 参照: 認証済みユーザーは全行参照可
CREATE POLICY "誰でもプロフィールを参照できる"
  ON profiles FOR SELECT TO authenticated USING (true);

-- 作成・更新: 自分のレコードのみ
CREATE POLICY "自分のプロフィールのみ作成できる"
  ON profiles FOR INSERT TO authenticated WITH CHECK (auth.uid() = id);
CREATE POLICY "自分のプロフィールのみ更新できる"
  ON profiles FOR UPDATE TO authenticated USING (auth.uid() = id) WITH CHECK (auth.uid() = id);
```

- 履歴は一切上げない（誰といつ会ったかはローカル DB のみ）。
- フロントは未読 user_id 一覧を `.in('id', [...])` でまとめて取得する。
- 詳細とアクセス制御は [specs/profile-sync.md](./specs/profile-sync.md)。

`avatar_code` は **`b{NN}_h{NN}_o{NN}_f{NN}` 形式の固定 15 文字**（base / hair / outfit / face の 4 軸、各 2 桁ゼロ埋め）。表情 (face) は MVP から提供（スマイル / 驚き / どや顔 / ウインク）。
将来 `a{NN}`（accessory）軸を追加する場合は、後方互換のため **未知の軸はパーサが無視する** ルールとする。詳細は [specs/avatar.md](./specs/avatar.md)。

### 4.4 起動時の対面挨拶シーンの上限と「会いにいく」フロー

未読データの開示は **「サプライズ感」を保ちつつ、現実的な視聴限界を超えないこと** を両立する設計とする。

- **オフライン時はそもそも開示しない**:
  - プロフィール fetch 未完了の相手は対面挨拶にも広場にも一切出さない（[specs/profile-sync.md](./specs/profile-sync.md) §4）。
  - オンライン復帰後、初めて完璧な状態（名前・アバター・メッセージ揃い）でポップアップに登場する。
- **1 セッションあたりの挨拶上限**: **20 人**
  - 起動時に「fetch 完了かつ未挨拶」が 20 人以下なら、全員と順次対面挨拶。
  - 21 人以上ある場合、最初の 20 人だけ挨拶し、セッション終了画面に **「あと N 人に会いにいく」ボタン** を出す。
- **「会いにいく」ボタン**:
  - 押下で **次の 20 人** をさらに連続対面挨拶。
  - 残数がゼロになるまで何度でも繰り返せる。
  - 押さなければ、未表示の未読は **次回起動時の冒頭** に持ち越される（最大 20 人ルールを再適用）。
- **広場への合流**:
  - 全員と挨拶し終わったタイミングで、ユーザー + 挨拶相手 全員が **ゲートをくぐる動作** に入り、カメラパン + クロスフェードで **広場ビュー（[specs/encounter-plaza.md](./specs/encounter-plaza.md)）** に到着する。
  - 広場到着後は合流アバターが画面左端から順次フレームインし、各自のアイドリング状態に入る。

詳細は [specs/encounter-popup.md](./specs/encounter-popup.md) と [specs/encounter-plaza.md](./specs/encounter-plaza.md) に記載する。

## 5. データ設計（ローカル SQLite スキーマ）

履歴とアプリ設定はすべて端末ローカル SQLite に保存される。**Supabase に上がるのは公開プロフィールのみ**で、すれ違い履歴（誰といつ会ったか）はクラウドへ送信しない。

### `my_profile` テーブル (自己データ)

| カラム | 型 |
| --- | --- |
| `user_id` | UUID |
| `display_name` | String |
| `avatar_code` | String |
| `message` | String |
| `home_prefecture` | String `null` 可 ("01"〜"47"。任意項目、[specs/regional-map.md](./specs/regional-map.md)) |

### `encounter_logs` テーブル (トランザクション履歴)

| カラム | 型 |
| --- | --- |
| `log_id` | PK |
| `encountered_user_id` | FK |
| `encountered_at` | Timestamp |
| `is_read` | Boolean（未読/既読フラグ） |

### `users_cache` テーブル (すれ違った相手のプロフィール)

| カラム | 型 |
| --- | --- |
| `user_id` | PK |
| `display_name` | String |
| `avatar_code` | String（`b{NN}_h{NN}_o{NN}_f{NN}` 形式、15 文字） |
| `message` | String |
| `home_prefecture` | String `null` 可 (相手の出身県、[specs/regional-map.md](./specs/regional-map.md)) |
| `encounter_count` | Integer |

> `avatar_code` のフォーマットと描画方式は [specs/avatar.md](./specs/avatar.md) を参照。
> 未知のパーツ ID を受信した場合は **デフォルトパーツにフォールバック** してクラッシュしない方針とする。

## 6. 法的・セキュリティ要件

- **位置情報の非取得**: GPS や CoreLocation などの座標データは一切取得・保存・送信しない。物理的な電波の到達のみを「すれ違い」の証明とする。
- **知的財産権の回避**:
  - 「すれ違い通信」「StreetPass」「Mii パレード」等の商標・固有名詞は使用しない。
  - Mii のような意匠の直接模倣は避け、フラットベクターの独自キャラクターを採用する（[specs/avatar.md](./specs/avatar.md)）。
- **プライバシー**:
  - **すれ違い履歴は端末ローカルにのみ保存**し、中央サーバーへアップロードしない（誰といつ会ったかは外部に出ない）。
  - **公開プロフィール (display_name / avatar_code / message) は Supabase に保存される**。これは BLE で受信した相手の `user_id` から名前・アバター・メッセージを取得するため。プロフィール非公開モードや退会時の削除フローは [specs/profile-sync.md](./specs/profile-sync.md) で別途定義する。
  - 初回起動はゲストで開始し、工房でプロフィール公開を選ぶ時に **明示的同意とコミュニティルール同意** を求める。同意なしには BLE すれ違い機能を起動しない。
